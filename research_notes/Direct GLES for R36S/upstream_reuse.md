# GZDoom GLES donor architecture and practical reuse

## Which upstream should supply code, and which architecture fits Zandronum?

### Takeaway
Use pinned current GZDoom GLES implementation as donor/reference for low-level GLES submission, shader compilation, texture upload, and state handling; retain Zandronum scene traversal, gameplay, actors, saves and networking. Bulk-copying GZDoom's complete renderer would pull in several generations of engine abstractions and still would not establish full feature correctness.

### Cited Findings
- Historical `ZDoom/gzdoom-gles` README explicitly says all contents merged into GZDoom 4.7.0; original history is `oldmaster`; repository archived July 24, 2022. The old project is not a separately maintained older-engine GLES implementation. — [README](https://github.com/ZDoom/gzdoom-gles/blob/7e08ec0b4c59a4a58b993178a4bc737cd1121c47/README.md#L1-L4), [repository](https://github.com/ZDoom/gzdoom-gles).
- Exact pins fetched October 15, 2026: current GZDoom master `c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7`; archive master `7e08ec0b4c59a4a58b993178a4bc737cd1121c47`; historical `oldmaster` `6329e6609747db35c67d980b1a9a7e2264be3edb`; GLES 4.6.1 tag `146e388430ece26258dba6d32b61ff3f5431a905`. Local clones under `.scratch/gles/gzdoom` and `.scratch/gles/gzdoom-gles`. — [current pin](https://github.com/ZDoom/gzdoom/commit/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7), [historical tip](https://github.com/ZDoom/gzdoom-gles/commit/6329e6609747db35c67d980b1a9a7e2264be3edb), [4.6.1](https://github.com/ZDoom/gzdoom-gles/commit/146e388430ece26258dba6d32b61ff3f5431a905).
- First historical GLES-specific addition is February 18, 2021, `903f305763c78e24a41f4aaee280bde4e1bf870f`, “Duplicated GL to GLES. Compiles and runs”; integration commit `441cd0796f69423c043aadfa0ab5dc5a1ccca2de` modifies 116 files with 12,502 insertions. It is already based on modern GZDoom shared rendering architecture. — [first commit](https://github.com/ZDoom/gzdoom-gles/commit/903f305763c78e24a41f4aaee280bde4e1bf870f), [integration](https://github.com/ZDoom/gzdoom-gles/commit/441cd0796f69423c043aadfa0ab5dc5a1ccca2de).
- Current source remains under `src/common/rendering/gles`; shader resources under `wadsrc/static/shaders_gles`. `FGLRenderState` derives from modern abstract `FRenderState`, uses `FMaterial`, `IVertexBuffer`, `IIndexBuffer`, `HWViewpointUniforms`, and shared `hwrenderer` facilities. `GLBuffer` implements `IBuffer`; `GLVertexBuffer` implements `IVertexBuffer`. — [state interface](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_renderstate.h#L28-L89), [buffers](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_buffers.h#L1-L110).
- Zandronum base `178fbce175adc2cc3fca645d66d4c9bebaf5d8b1` has older concrete `FRenderState` holding texture/fog/glow/dynamic-light/blend/alpha state and maintaining fixed-function fallback. Its vertex shader relies on `gl_Vertex`, `gl_Color`, `gl_TextureMatrix`, `gl_ModelViewMatrix`, `gl_NormalMatrix`, and `ftransform()`. — [local state](https://github.com/ktodorow/zandronum_arm64/blob/178fbce175adc2cc3fca645d66d4c9bebaf5d8b1/src/gl/renderer/gl_renderstate.h#L92), [local shader](https://github.com/ktodorow/zandronum_arm64/blob/178fbce175adc2cc3fca645d66d4c9bebaf5d8b1/wadsrc/static/shaders/glsl/main.vp#L16-L75).
- Donor no-map path keeps CPU staging memory, uploads through `glBufferSubData`, and sets generic vertex attributes through `glVertexAttribPointer`; indexed drawing uses triangles/strips/fans/lines/points rather than quads. Shader render state uploads matrices through `glUniformMatrix4fv`. — [buffer upload](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_buffers.cpp#L96-L164), [attributes](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_buffers.cpp#L272-L323), [draw methods](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_renderstate.cpp#L545-L566), [matrix uniform](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_renderstate.cpp#L50-L57).

### Inferences
- Preferred design: engine-owned GLES adapter matching existing renderer's finite call/state vocabulary, not externally interposed desktop GL library. Existing scene functions can initially retain Begin/End-style intent, but adapter must accumulate vertices, normalize quads/fans/strips into GLES primitives, and submit buffered draws with explicit attribute/uniform contracts. It must know renderer boundaries and enforce flush-on-material/blend/matrix/stencil/FBO changes. Cross-surface batching should be restricted to equal-state opaque work; translucent/portal ordering preserved.
- Porting the entire modern `hwrenderer` to make donor compile would greatly enlarge gameplay/header/data-structure change surface. Keeping old scene generation minimizes risk to existing Zandronum network/save behavior, though those invariants still need test evidence.
- `gles_buffers.cpp` is useful algorithmic donor, not drop-in class: local adapter can reuse upload/attribute structure without importing donor abstract buffer framework or models' packed-normal issues.

### Gaps
- Device GPU/driver capabilities must come from actual device query, not retailer identity. R36S names cover different hardware; recalled project device reports Mali-G31, but this researcher did not run the device probe.
- No evidence yet that removing GL4ES alone provides sustained 60 FPS. Donor architecture does not prove this workload's frame-time budget.

## Which donor components are reusable, and what must a complete port implement?

### Takeaway
Reuse permissive low-level components where their data contracts fit; adapt existing local GLSL to explicit GLES attributes/uniforms. GLES2/GLSL100 is real donor baseline, but ES3 can simplify this specific device if confirmed; donor feature omissions must not become silent Zandronum regressions.

### Cited Findings
- Donor GLES context requests ES profile major version 2. Loader has `libGLESv2_CM.so`, `libGLESv2.so`, `libGLESv2.so.2` fallbacks; GLES mode chooses GLSL version `100`, queries NPOT and packed-depth-stencil/depth-clamp/anisotropy extensions, and defaults `gles_use_mapped_buffer` false. — [context](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/platform/posix/sdl/sdlglvideo.cpp#L210-L229), [loader/capabilities](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_system.cpp#L8-L236).
- Donor explicitly sets `gl_customshader = false`. Fragment shader clip-distance discard line is commented out. Buffer attribute table has TODO that `GL_INT_2_10_10_10_REV` means model normals will be broken. PostProcessScene only binds current framebuffer and runs after-bloom callback, rather than implementing full desktop postprocessing. These are source observations, not a claim every relevant feature necessarily fails in every map. — [custom shaders disabled](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_system.cpp#L180-L187), [clip line](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/wadsrc/static/shaders_gles/glsl/main.fp#L470-L495), [normal TODO](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_buffers.cpp#L272-L278), [postprocessing](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_postprocess.cpp#L54-L60).
- Donor shader variants are looked up by `CreateShaderTag`; first use compiles variant with texture, fog, lights, desaturation, glow, colormap and other preprocessor defines; later calls reuse cached variant. This moves conditions out of fragment runtime at cost of first-use compilation. — [FShader::Bind](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_shader.cpp#L682-L735).
- Donor dynamic lights are uploaded as uniform vec4 arrays, default 32 lights/surface; mapped-buffer sync only runs for desktop modes, not GLES mode. — [light uploads](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_renderstate.cpp#L330-L347), [default limit](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_system.cpp#L8-L10), [sync guard](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_buffers.cpp#L235-L266).
- Texture CreateTexture uses unsized `GL_RGBA` (or `GL_ALPHA` for 1-byte texture); Bind/Unbind track bound IDs; sampler helper maps clamp/filter/mipmap settings to GLES `glTexParameteri`. — [texture](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_hwtexture.cpp#L78-L180), [binding cache](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_hwtexture.cpp#L226-L268), [sampler](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_samplers.cpp#L66-L180).

### Inferences
Practical reuse map (all donor references pinned above):

| Donor file/functions | Practical integration | Boundary |
| --- | --- | --- |
| `gles_buffers.cpp`: `GLBuffer::SetData`, `Upload`, `GLVertexBuffer::SetFormat`, `Bind` | Adapt VBO staging/upload/attribute setup for local packed vertex struct | Do not import abstract interfaces; fix ownership/alignment; use legal GLES index formats; no unsafe unsynchronized map default |
| `gles_hwtexture.cpp`: `CreateTexture`, `Bind`, `UnbindAll` | Adapt legal GLES formats, upload, cache reset and context-loss cleanup into existing local texture class | Preserve translation/brightmap/canvas semantics; no format fallback silently losing alpha |
| `gles_samplers.cpp`: `FSamplerManager::Bind` | Adapt clamp/filter/mipmap table into existing local texture state | Avoid repeated parameter changes when unchanged; NPOT restrictions require query |
| `gles_shaderprogram.cpp`: compile/link/log/resource cleanup | Port minimal zlib-licensed compiler helper with local resource loader | Modern filesystem/error APIs need substitutions |
| `gles_renderstate.cpp`: matrix/uniform/blend/state approach | Reference or separately licensed adaptation of selected methods | LGPL notice/combined-work requirements apply; modern FRenderState not local FRenderState |
| `gles_shader.cpp`: precision/variant/caching concepts | Reference for ES declarations and tag-keyed variants | LGPL obligations apply; do not lazy-compile new runtime variants during gameplay without warmup |
| `wadsrc/static/shaders_gles` | Read as architecture reference; use local shaders as implementation basis | No blind wholesale import under ambiguous/per-repo GPLv3 terms |
| modern full framebuffer/shared scene classes | Avoid whole-copy | Large engine/API dependency closure; platform integration differs |

Concrete release implementation sequence:
1. Lock build/runtime backend selector and explicit GLES context, load GLES directly, log actual GL strings/capabilities. Native 640x480 and current lifecycle/input/audio retained. No GL4ES dependency in selected GLES process.
2. Add explicit renderer vertex contract: position, UV, color, local fog/glow/light attributes, matrix uniforms and tracked constant attributes. Implement quads, triangles, strips, fans, lines, model indexed arrays, matrix stack, texture matrices, sphere mapping and state flushing. Buffer allocation/reuse must remain bounded and error-checked.
3. Adapt local shader semantics to GLES: alpha discard replacing alpha test, fog/light/glow/brightmaps/colormaps/invulnerability/fuzz/warps, uniforms replacing desktop builtins, correct texture unit limits. Compile required built-in variants before level gameplay; log full compile/link errors. Preserve original visual semantics before optional optimizations.
4. Route all surfaces and 2D paths: walls/flats/slopes/3D floors/skies/decals/particles/sprites/models/voxels/HUD/console/menu/automap/screenshots/wipes/render-to-texture/camera textures. Implement stencil and clip-plane semantics for mirrors and portals; donor commented clip code cannot be treated as completed support.
5. Reuse donor GLES texture/sampler details selectively; confirm renderbuffer depth/stencil setup; protect batching from framebuffer/readback/upload/state mutations. Honor saved settings and server-enforced video defaults.
6. Test deterministic original missing-surface save plus representative advanced features and gameplay/network invariants, desktop Mesa software GLES and actual Mali; measure CPU/frame time, misses, p95/p99, first-use spikes and warm vs cold launch. Retain existing backends while GLES qualifies, then set release default only after evidence meets agreed release bar.

### Gaps
- Device extension limits, ES3 context creation, uniform/attribute counts, stencil, FBO and index support are unmeasured here; another researcher owns device audit.
- Complete custom mod shader compatibility cannot be inferred from donor; desktop GLSL user shader conversion requires defined compatibility behavior or explicit release limitation, not silent disablement.

## Which licenses permit redistribution and maximum safe reuse?

### Takeaway
Whole-repository GPLv3 label does not erase explicit BSD/zlib/LGPL file licenses. Preserve and record per-file provenance; import clear permissive pieces, keep local shader lineage, and avoid creating GPLv3-only combined engine until legacy-source obligations have been audited.

### Cited Findings
- Zandronum README says its GPL-compatible Sleepycat-derived license covers **Zandronum-specific code only**, with per-source notices governing other code. LICENSE.txt requires notices, no endorsement, complete-source availability for binary distributions. — [README](https://github.com/ktodorow/zandronum_arm64/blob/178fbce175adc2cc3fca645d66d4c9bebaf5d8b1/README.md#L46-L53), [license](https://github.com/ktodorow/zandronum_arm64/blob/178fbce175adc2cc3fca645d66d4c9bebaf5d8b1/LICENSE.txt#L1-L28).
- Existing engine `doomdef.h` and `p_mobj.cpp` retain DOOM Source Code License notices. Existing `gl_renderstate.cpp` has author conditions including LGPL2.1+ outside GZDoom/derivatives and mandatory full source disclosure. These are not evidence of a blanket engine-wide GPLv3 grant. — [doomdef](https://github.com/ktodorow/zandronum_arm64/blob/178fbce175adc2cc3fca645d66d4c9bebaf5d8b1/src/doomdef.h#L1-L15), [p_mobj](https://github.com/ktodorow/zandronum_arm64/blob/178fbce175adc2cc3fca645d66d4c9bebaf5d8b1/src/p_mobj.cpp#L1-L17), [renderer](https://github.com/ktodorow/zandronum_arm64/blob/178fbce175adc2cc3fca645d66d4c9bebaf5d8b1/src/gl/renderer/gl_renderstate.cpp#L1-L42).
- Current donor `gles_buffers.cpp`, `gles_hwtexture.cpp`, `gles_samplers.cpp`, `gles_framebuffer.cpp`, and `gles_renderer.cpp` have explicit 3-clause BSD notices; `gles_shaderprogram.cpp`, `gles_postprocess.cpp`, `gles_postprocessstate.cpp`, and `gles_renderbuffers.cpp` have explicit zlib-style notices requiring origin honesty and altered-source marking. — [buffers notice](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_buffers.cpp#L1-L34), [texture notice](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_hwtexture.cpp#L1-L34), [sampler notice](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_samplers.cpp#L1-L35), [compiler notice](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_shaderprogram.cpp#L1-L21).
- Donor `gles_renderstate.cpp/.h` and `gles_shader.cpp/.h` explicitly say GNU **Lesser** GPL version 2 or later. This differs from upstream project's top-level GPLv3. — [renderstate notice](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_renderstate.cpp#L1-L20), [shader notice](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/src/common/rendering/gles/gles_shader.cpp#L1-L20), [root license](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/LICENSE).
- Donor GLSL `main.fp/.vp` have no individual notice at file start. GZDoom licensing README says all script code in `gzdoom.pk3` is GPLv3 unless otherwise noted; it does not explicitly carve out these GLES resources. — [fragment](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/wadsrc/static/shaders_gles/glsl/main.fp#L1-L26), [vertex](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/wadsrc/static/shaders_gles/glsl/main.vp#L1-L28), [licensing README](https://github.com/ZDoom/gzdoom/blob/c26ce2e6ca2a0c770f140cb25dde0d30073ca8f7/docs/licenses/README.TXT#L1-L28).
- Historical GZDoom GPL transition removed FMOD as final GPL-incompatible piece and replaced old Doom/Raven headers. That demonstrates why merely copying latest license text would not be sound conversion of older combined engine. — [FMOD removal](https://github.com/ZDoom/gzdoom-gles/commit/c219811a542e0d6aae38b920ae9e257c5c2286c1), [header conversion](https://github.com/ZDoom/gzdoom-gles/commit/96d328de9baaf4c9ed3244846a394b60e912ab6c).

### Inferences
- Immediate feasible route: adapt explicit BSD/zlib low-level donor code and include original notices; identify adapted functions, donor path and full SHA in provenance manifest. Include corresponding license text and source availability in package. Keep local shader sources and semantics, adapting them to GLES from specification and architecture findings.
- LGPL files can potentially be used under LGPL combined-work terms rather than upgrading entire application to GPLv3, but this requires actual notice, modified-library/source, relink/rebuild and reverse-engineering-rights compliance. Building source-available project does not automatically finish those obligations. For minimal first integration risk, prefer independently implemented local state/shader adaptations and permissive compiler/buffer helpers.
- No finding establishes all present Zandronum code GPLv3-compatible. Old Doom/Raven-derived grants may have alternative permissions, but blanket GPLv3 import should be gated by complete provenance/license audit. This is a distribution boundary, not a blocker to direct GLES implementation.
- Read-only comparison with donor GPL resources is not a license to copy their expression. New shader implementation should be grounded in existing local source and necessary GLES language/API conversion, with source lineage documented.

### Gaps
- No complete project-wide legacy license audit performed. Whether every ancestor/file has compatible alternative grants remains unproven.
- No upstream author confirmation found explicitly licensing GLES shader assets under permissive terms; do not assert they are BSD solely because adjacent C++ files are BSD.
