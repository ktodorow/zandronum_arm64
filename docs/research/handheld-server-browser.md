# R36S server browsing and content setup

Checked 2026-10-14. Zandronum source inspected at release Git commit `28f736fb3f77bf0b767ec5468191bc05d0fccbb9` (official Mercurial tag `ZA_3.2.1`); Doomseeker at stable 1.5.3 commit `59617ba689a66a319ab98b543e8188cf474f7640`. These are source findings, not a successful handheld runtime test. No game-server queries, mod downloads, firmware changes, or builds were performed.

## Existing engine capability

**Zandronum 3.2.1 already has an in-engine graphical server browser.** `ZA_Browser` supplies server-type/game-type filters, sorting, empty/full filters, a name field, eight server slots, refresh, details and join. It is not necessary to add Doomseeker just to obtain a public list. `BROWSER_QueryMasterServer()` sends the existing launcher/master protocol challenge and version; the engine then queries returned servers. [Release menu definition](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/wadsrc/static/menudef.za#L352), [master query](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/browser.cpp#L802).

LAN discovery is also present, through reception of server broadcasts on a LAN socket. The engine's public refresh calls the master-query path; it should not be described as an active LAN scan. Servers broadcast if `sv_broadcast` is enabled. [LAN socket](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/network.cpp#L348), [server broadcast](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/sv_master.cpp#L641), [client reception](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/cl_main.cpp#L1089).

The server-list item implements the ordinary menu-event interface, including left/right page changes and a `fromcontroller` argument. This is evidence of a reusable menu path, not proof that every operation works with the R36S pad. Names are truncated to 12 characters plus an ellipsis and rows use the small font. Legibility, selection, paging, scrolling, and text entry need hardware testing. [Menu event](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/menu/browsermenu.cpp#L187), [row rendering](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/menu/browsermenu.cpp#L149).

## The content gap

Joining constructs `restart -connect <address> -iwad <name> -file <ordered server PWAD names>`. It searches for the PWADs locally using `D_AddFile`; the files do not have to be loaded in the current session. If any required PWAD cannot be found, it displays the missing names and returns. **This path does not download missing content.** The server's WAD URL is available for display, but it is not an implemented download workflow. [Join implementation](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/menu/browsermenu.cpp#L620), [details rendering](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/menu/browsermenu.cpp#L282).

There is also a preflight matching gap: the engine browser requests names and game-mode information, not `SQF2_PWAD_HASHES`; if hash data arrives, its parser skips the strings. It also skips optional-WAD and DEH metadata. Thus a new download workflow must preserve file order and determine how to obtain/use server hashes, optional content, and patches. A same-name local file alone does not establish an exact content match. This observation concerns browser preflight; it does not imply the game connection bypasses its separate content checks. [Query flags](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/browser.cpp#L901), [skipped metadata](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/browser.cpp#L750).

The owner subsequently chose single-player first and multiplayer last. Preloaded owner-supplied content can support the initial single-player milestone. The later multiplayer milestone still requires browsing and setting up server content using only R36S controls. PortMaster launch is required for both milestones; a personal compatible package is sufficient, and public submission is not required.

## Reusable Doomseeker and Wadseeker work

Doomseeker is an existing Qt desktop server browser with a Zandronum plugin. Its stable source receives server PWAD MD5 hashes, checks found files, identifies missing/incompatible files, offers installation via Wadseeker, and passes connect/join passwords to the client. This is existing implementation to study/reuse, not an R36S-ready UI. [Plugin hash parsing](https://github.com/DoomseekerTeam/Doomseeker/blob/59617ba689a66a319ab98b543e8188cf474f7640/src/plugins/zandronum/zandronumserver.cpp#L780), [content check](https://github.com/DoomseekerTeam/Doomseeker/blob/59617ba689a66a319ab98b543e8188cf474f7640/src/core/serverapi/gameclientrunner.cpp#L300), [missing-file/install flow](https://github.com/DoomseekerTeam/Doomseeker/blob/59617ba689a66a319ab98b543e8188cf474f7640/src/core/gui/mainwindow.cpp#L630), [password arguments](https://github.com/DoomseekerTeam/Doomseeker/blob/59617ba689a66a319ab98b543e8188cf474f7640/src/plugins/zandronum/zandronumgamerunner.cpp#L34).

Wadseeker is a reusable library with no GUI, using QtCore/QtNetwork. It searches configured/common sites including `/idgames`, supports concurrent downloads and ZIP/7z archives, and blocks searches for known commercial IWAD names. Checksums can be supplied; its file validator rejects a mismatch, but an empty checksum list cannot verify identity. A missing commercial IWAD requires the user's supplied file; Doomseeker also has a separate Freedoom replacement workflow, whose compatibility must be considered per server. [Official Wadseeker description](https://doomseeker.drdteam.org/wadseeker.php), [checksum validator](https://github.com/DoomseekerTeam/Doomseeker/blob/59617ba689a66a319ab98b543e8188cf474f7640/src/wadseeker/entities/waddownloadinfo.cpp#L176), [missing/optional/Freedoom UI](https://github.com/DoomseekerTeam/Doomseeker/blob/59617ba689a66a319ab98b543e8188cf474f7640/src/core/gui/missingwadsdialog.cpp#L110).

ARM64 is not an unexplored Doomseeker architecture: the first-party DRD repository advertises ARM64 packages, lists Doomseeker, its Zandronum plugin and Wadseeker, and targets Ubuntu 22.04+/Debian 12+. Its Zandronum **client** package is explicitly x86-only. ARM64 Doomseeker availability therefore does not solve the ARM64 playable engine. [DRD packages](https://debian.drdteam.org/).

Doomseeker's CMake supports Qt5/Qt6, and its GUI requires Widgets, Gui, Multimedia, Network and Xml. Wadseeker's runtime library has the smaller Core/Network dependency set; its build also uses LinguistTools and compression components. A bounded source search for `gamepad`, `joystick` and `QGamepad` found no direct pad-control implementation apart from an icon name; controller usability remains unverified. [Qt selection](https://github.com/DoomseekerTeam/Doomseeker/blob/59617ba689a66a319ab98b543e8188cf474f7640/cmake/Modules/Macros.cmake#L156), [GUI dependencies](https://github.com/DoomseekerTeam/Doomseeker/blob/59617ba689a66a319ab98b543e8188cf474f7640/src/core/CMakeLists.txt#L67), [library dependencies](https://github.com/DoomseekerTeam/Doomseeker/blob/59617ba689a66a319ab98b543e8188cf474f7640/src/wadseeker/CMakeLists.txt#L51).

## dArkOS constraints and architecture choice

dArkOS is Debian based and its build supports 64-bit plus optional 32-bit userspace for PortMaster ports. Its source includes `gptokeyb` and an ASCII on-screen keyboard intended to be wrapped for pad navigation. These are candidate helpers; their presence/version and usable display/input handoff on the actual installed device need inspection. [dArkOS README](https://github.com/christianhaitian/dArkOS/blob/7b91fe0f37c82ed861482173d3cbec8ed1966f09/README.md), [helper packaging](https://github.com/christianhaitian/dArkOS/blob/7b91fe0f37c82ed861482173d3cbec8ed1966f09/build_gptokeyb.sh), [OSK](https://github.com/christianhaitian/dArkOS/blob/7b91fe0f37c82ed861482173d3cbec8ed1966f09/inttools/osk.py).

An ARM64 Qt package alone does not guarantee output on the handheld. Qt embedded platforms include EGLFS, LinuxFB and Wayland; enabled plugins and board graphics determine availability. QWidget applications can use EGLFS, with CPU-rendered widgets composed into a fullscreen window; LinuxFB provides software rendering. Test the actual display backend, input permissions, memory use, dialogs and focus before choosing the whole Doomseeker GUI. [Qt embedded Linux](https://doc.qt.io/qt-6/embedded-linux.html).

| Approach | Existing work retained | New work / uncertainty |
| --- | --- | --- |
| PortMaster launches engine; extend its browser/content flow | Public discovery, LAN broadcasts, menu list, local-content restart | Controller text entry and readable details; metadata/checksum retention; download helper/UI; errors, cache and restart handoff |
| PortMaster launches adapted Doomseeker then engine | Query plugins, content validation/download workflow, password handling | Qt runtime/display deployment; desktop UI adaptation; controller navigation and text entry; engine handoff |
| New controller-first external browser | Existing query protocol and reusable Wadseeker | A new application for discovery, lists, filtering, joining and state; not currently provided by this port |

Recommendation for the next investigation: retain the engine browser unless device testing proves it unsuitable, and prototype the content gap through a small helper or integration using established Wadseeker behavior. No separate full browser is required by the current facts. This is a proposed architecture, not a committed or implemented feature. Linking/integration choices must also be checked against the components' LGPL/GPL terms before distribution.

## Interview outcome and remaining implementation questions

The user selected public/LAN discovery, filters/details, manual connection and controller text entry; automatic retrieval/matching of available missing or mismatched server add-ons; and explicit download failures. The owner will provide Doom/Doom II IWADs later. Favorites/history and full Doomseeker feature parity are deferred. See the [design record](../arm-port-design.md). The following technical questions guide implementation rather than reopen that scope:

- How will exact downloadable missing/mismatched server add-ons be retrieved, validated and joined in one controller-only flow?
- How should incompatible non-3.2.1 servers be presented or filtered?
- How are player names, filter text, manual addresses and both connect/join passwords entered? A built-in ASCII OSK versus a firmware helper is still a design choice.
- Locate the original-game IWADs after the owner places them in the handheld's Doom folder.
- What should happen for unavailable downloads, wrong hashes, optional WADs, large archives, insufficient storage, cancellation and cached versions with identical names?

The later multiplayer acceptance must include an actual controller-only path from PortMaster launch through discovery, a server requiring absent downloadable content, installation/matching, successful stock-3.2.1 join, and return to the launcher. These tests follow acceptance of single-player gameplay and do not gate that first milestone. Network/server compatibility and content availability remain separate runtime gates. See the amended [specification](../specs/zandronum-3.2.1-arm64-r36s.md).
