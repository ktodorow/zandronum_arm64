# Current ARM fork audit

Research date: 2026-10-14. Scope: the existing repository, its public origin and immediate parent, and selected upstream release source. This is source and history research; no configure, compilation, game launch, or multiplayer test was performed. No source files or branches were changed.

## Findings that affect the plan

The existing `master` is an old **3.1-alpha internal build source tree**, not Zandronum 3.2.1. Its ARM work is useful as a reference, especially the OpenAL backend, portable CPU path, and alignment fixes. The repository name `zandronum_arm64` is not evidence of a working AArch64 client. The strongest documented platform history is the Pandora/32-bit ARM Linux port. [Version definitions](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/version.h#L45-L67), [fork README](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/README.md#L3-L7), [platform compiler options](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/CMakeLists.txt#L27-L62).

**Recommendation, accepted during the design interview:** start the generic ARM client from the exact upstream 3.2.1 release commit and transplant the fixes it actually needs. Keep this old fork as a historical reference. Advancing this snapshot to 3.2.1 would require importing all intervening gameplay/network/build changes as well as validating ARM; applying a smaller reviewed portability change set onto the release avoids reconstructing that upgrade. This is an engineering inference, not a measured patch-size comparison. The identified upstream commit `28f736fb3f77bf0b767ec5468191bc05d0fccbb9` declares `GAMEVER_STRING "3.2.1"` and `BUILD_RELEASE`; its source also already contains CMake 4 compatibility changes that this fork lacks. [Release version](https://github.com/torrsamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/version.h#L43-L78), [release build source](https://github.com/torrsamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/CMakeLists.txt#L1-L21).

## Existing client path and portability work

The tree has a graphical client path. On Linux, `SERVERONLY=ON` enables `SERVER_ONLY`, removes sound/GTK/OpenGL, and changes the executable name to `zandronum-server`. Such a build does not satisfy the playable-client goal. `SERVERONLY=OFF` is the relevant path; `NO_GL=ON` can still select the software renderer. Non-Windows builds still require SDL even for the server configuration. [Server/client options](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/CMakeLists.txt#L224-L315), [software renderer selection](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/sdl/hardware.cpp#L145-L163).

Several pieces already accommodate non-x86 CPUs: `NO_ASM` defaults to ON, SSE support is checked before selecting SSE-specific sources, `x86.cpp` has a non-x86 CPU-info stub, and fixed-point arithmetic chooses `basicinlines.h` outside selected x86 compiler combinations. These are meaningful source provisions; they do not prove an ARM binary works. [Assembly/SSE configuration](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/CMakeLists.txt#L17-L22), [SSE sources](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/CMakeLists.txt#L877-L887), [CPU stub](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/x86.cpp#L10-L20), [arithmetic dispatch](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/m_fixed.h#L13-L21).

The board options for Pyra, RPi2/3/4, GameShell, and ODroid use combinations of `-marm`, `-mfpu`, `-mfloat-abi=hard`, and `-fsigned-char`. These options target 32-bit ARM compiler conventions; enabling them wholesale is not a generic AArch64 solution. A generic target needs explicit architecture/ABI handling, and signedness must be checked separately from board tuning. [Board flags](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/CMakeLists.txt#L27-L62).

ACS array loading contains `memcpy` fixes guarded only by `__arm__`, alongside a comment about optimizer/undefined-behavior concerns. AArch64 does not select that specific override. This is an alignment/aliasing audit target, not proof of an AArch64 crash: the generic integer accessors already read individual bytes on non-x86 architectures. [ACS fixes](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/p_acs.cpp#L2210-L2264), [generic byte accessors](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/m_swap.h#L179-L207).

Pandora-specific fullscreen, 800×480 defaults/limits, keyboard bindings, and smaller GL depth buffer are also present. Those should be treated as device policy rather than generic ARM necessities. The SDL joystick implementation can provide a starting point for handheld controls, but an R36S mapping and deadzone choice have not been validated. [Video defaults](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/v_video.cpp#L156-L163), [display policy](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/sdl/hardware.cpp#L169-L192), [bindings](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/c_bind.cpp#L78-L92), [joystick implementation](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/sdl/i_joystick.cpp#L1-L124).

## Graphics and audio are separate client risks

The video source uses SDL 1.2-era calls including `SDL_SetVideoMode`, `SDL_WM_SetCaption`, and `SDL_GL_SwapBuffers`. When OpenGL is enabled, configuration requires desktop OpenGL and GLU. The fork README explicitly says it has no native GLES implementation and describes using gl4es on Pandora/ODroid. For a handheld OS with GLES/DRM rather than desktop GL/X11, the window/display path must therefore be researched separately from CPU compilation. Software rendering may be a useful initial milestone, but its performance and display integration still need measurement. [SDL video](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/sdl/sdlvideo.cpp#L297-L327), [GL context/output](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/sdl/sdlglvideo.cpp#L289-L360), [OpenGL dependency checks](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/CMakeLists.txt#L324-L334), [README](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/README.md#L5-L7).

OpenAL is valuable work in this fork: Linux discovers it through pkg-config; FMOD can be disabled with `NO_FMOD`. If neither backend is present, the default becomes `null`, so a compiling binary can silently fail the intended audio capability. `libsndfile` and `mpg123` conditionally enable decoders; `SoundRenderer::CreateDecoder` returns null when neither can decode the stream. Validate sound effects, MIDI/music, and compressed music rather than only verifying that OpenAL initializes. GME, DUMB, FluidSynth, compression libraries, and OpenSSL also appear in the build. [Audio backend selection](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/sound/i_sound.cpp#L89-L99), [dependency detection](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/CMakeLists.txt#L274-L280), [decoder behavior](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/sound/i_sound.cpp#L546-L574), [libraries](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/CMakeLists.txt#L714-L750).

## Build and validation limitations

- **Observed environment limitation:** this host reports `arm64`, has `/usr/bin/clang`, and has no `cmake`, `pkg-config`, or `hg` available on PATH. No local build result is claimed. No target R36S or Linux dependency set was inspected.
- **Known modern CMake incompatibilities by inspection:** this fork repeatedly requests CMake 2.4 policies and reads build-target `LOCATION`. CMake 4 removes compatibility below policy version 3.5 and removes CMP0026's old `LOCATION` behavior. Modernization or a suitable older toolchain is needed; merely raising the version declaration is insufficient. This was not reproduced locally. [Root build script](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/CMakeLists.txt#L1-L2), [target location reads](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/CMakeLists.txt#L64-L69), [official minimum-version documentation](https://cmake.org/cmake/help/latest/command/cmake_minimum_required.html), [official CMP0026 documentation](https://cmake.org/cmake/help/latest/policy/CMP0026.html).
- **Cross-compilation setup is historical:** `IMPORT_EXECUTABLES` must point to a native tool export, while the committed example contains absolute `/media/sda1/sources/hg/zandronum/...` paths. It cannot be assumed usable on this host; native tools and architecture-sensitive generated floating-point files need deliberate handling. [Cross build setup](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/CMakeLists.txt#L16-L25), [committed imported executables](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/ImportExecutables.cmake), [gdtoa generator path](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/gdtoa/CMakeLists.txt#L26-L46).
- **Revision metadata needs care:** the old generator invokes Mercurial despite this Git checkout. On failure with no generated header, its initialized timestamp/revision remains zero. The old internal source derives `NETGAMEVERSION` from that revision, and the old server checks it. The separate [3.2.1 release audit](upstream-3.2.1.md#revision-metadata-affects-stock-server-compatibility) confirms that the stable release also checks the revision-derived protocol byte unconditionally. Preserve the correct release metadata and confirm actual compatibility with an unmodified official server; no runtime connection test has been performed. [Generator](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/tools/updaterevision/updaterevision.c#L43-L67), [fallback/output](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/tools/updaterevision/updaterevision.c#L105-L170), [old protocol definition](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/version.h#L73-L84), [old server check](https://github.com/ktodorow/zandronum_arm64/blob/92dad02ccd1abe1ed49f93e6f7c16641cf0f20d1/src/sv_main.cpp#L1791-L1801).

## Evidence needed before calling the new port playable

Proposed acceptance evidence, to settle during the interview: an architecture-identifiable 3.2.1 executable and matching resource PK3; a clean reproducible client build; launch and map load with a legal IWAD; responsive input; sound effects and required music formats; successful connection and gameplay against an official 3.2.1 server; representative required mods; and repeated map changes/save-load without crashes. The R36S branch additionally needs an identified OS image and userspace ABI, measured frame time/RAM/temperature at its target resolution, working controls/menu navigation, a usable launch/exit flow, and its actual network solution. These are proposed checks, not completed results.

The interview has selected Linux ARM64 first, starting from official 3.2.1 with selective legacy fixes. ARM CPU architecture alone does not select the graphics stack, dependency ABI, or packaging; the installed dArkOS image still needs to identify the device target. See the [design interview record](../arm-port-design.md) for current decisions.
