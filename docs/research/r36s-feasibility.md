# R36S / dArkOS feasibility for a playable Zandronum 3.2.1 client

Checked: 2026-10-14. This is source and documentation research, not a device benchmark. No R36S was accessed, no game was built, and no dependencies or firmware were installed for this investigation.

**Subsequent device inspection:** read-only SSH checks in this session confirmed firmware `dArkOS (09022026)`, Debian 13 Trixie ARM64/glibc 2.41, SDL runtime 2.32.10, Mali-backed EGL/GLES/GBM, and installed PortMaster. See the [device snapshot](r36s-device-snapshot.md). The preference questions at the end were resolved in the [design interview record](../arm-port-design.md); renderer/frame-rate results remain untested.

## Scope from the interview

The user targets Linux ARM64 first, requires compatibility with unmodified official Zandronum 3.2.1 servers, wants base Doom/Doom II before mods, and initially wants personal builds for their own machines. Their R36S runs “DarkOS by christianhaitian.” The matching first-party project is spelled **dArkOS**. Keep that installed firmware as the target; a switch to another distribution is not part of the plan. Start from official 3.2.1 and selectively port reviewed legacy ARM fixes. The handheld target is native **640×480**, **30 FPS minimum with 60 FPS as the goal**. The renderer is undecided; the user wants accelerated OpenGL investigated if feasible.

**Assessment — inference:** a playable R36S client is plausible, but establishing a working ARM64 executable does not establish handheld support. dArkOS needs a compatible presentation path, sound, controls, launcher integration and measured performance. Desktop OpenGL through gl4es is a reasonable accelerated experiment because upstream uses legacy GL APIs. Software rendering is a useful comparison/fallback candidate. Neither has been validated here, and neither is known to achieve the requested native-resolution frame rate.

## Hardware and firmware facts

The ROCKNIX maintainers document the usual R35S/R36S platform as RK3326, quad Cortex-A35, Mali-G31, 1 GB RAM and a 640×480 3.5-inch display. Their table lists 1.3 GHz and no built-in connectivity. Treat those as the documented platform baseline rather than a guarantee about this specific unit, its governor, its clock or later hardware variants. The same page documents newer display variants. [ROCKNIX R35S/R36S device page](https://rocknix.org/devices/unbranded/game-console-r35s-r36s/)

dArkOS is Christian Haitian's Debian-based continuation of ArkOS. Its current build defaults to Debian Trixie with an ARM64 root filesystem and optional, enabled-by-default ARMHF compatibility. The bootstrap source explicitly uses `--arch=arm64`. This supports choosing an **AArch64 Linux** binary, not an Apple Silicon macOS binary or an ARMHF binary. [dArkOS README](https://github.com/christianhaitian/dArkOS/blob/7b91fe0f37c82ed861482173d3cbec8ed1966f09/README.md), [Makefile](https://github.com/christianhaitian/dArkOS/blob/7b91fe0f37c82ed861482173d3cbec8ed1966f09/Makefile), [root filesystem bootstrap](https://github.com/christianhaitian/dArkOS/blob/7b91fe0f37c82ed861482173d3cbec8ed1966f09/bootstrap_rootfs.sh)

The checked dArkOS build tree has an `rg351mp` RK3326 target, but no explicit `r36s` target. The current release list includes an RG351MP image. These observations do not disprove that the user's R36S runs dArkOS; they mean the exact image, update date, device tree and any adaptation are still unknown. Confirm them from the working installation before choosing the build environment. [RK3326 RG351MP build](https://github.com/christianhaitian/dArkOS/blob/7b91fe0f37c82ed861482173d3cbec8ed1966f09/build_rg351mp.sh), [dArkOS releases](https://github.com/christianhaitian/dArkOS/releases)

The RK3326 SDL2 build used by dArkOS enables KMSDRM and OpenGL ES and disables X11, Wayland and Vulkan. dArkOS installs proprietary `libMali` as EGL/GLES/GBM libraries. **Inference:** initially target fullscreen SDL2 + DRM/KMS + EGL/GLES. Do not assume an X11 desktop, GLX or a native desktop OpenGL compatibility context exists on the user's installation. ROCKNIX's Panfrost capabilities describe ROCKNIX and should not be transferred to dArkOS. [dArkOS SDL2 installer](https://github.com/christianhaitian/dArkOS/blob/7b91fe0f37c82ed861482173d3cbec8ed1966f09/build_sdl2.sh), [RK3326 SDL2 build recipe](https://github.com/christianhaitian/rk3326_core_builds/blob/85834eb07b4437d87adeaf6d47e05531ae97e8f2/scripts/sdl2.sh), [Mali library installation](https://github.com/christianhaitian/dArkOS/blob/7b91fe0f37c82ed861482173d3cbec8ed1966f09/build_deps.sh)

## What existing Doom support proves

dArkOS documents standalone LZDoom, standalone GZDoom and libretro PrBoom. Its GZDoom RK3326 recipe selects GZDoom 4.14.2, enables GLES2 and disables Vulkan; the launcher requests the GLES renderer. This is useful evidence about the firmware's intended graphics and input stack. It does **not** establish Zandronum support or Zandronum multiplayer compatibility. [dArkOS Doom support](https://github.com/christianhaitian/dArkOS/wiki/dArkOS-Emulators-and-Ports-information#doom), [GZDoom build recipe](https://github.com/christianhaitian/rk3326_core_builds/blob/85834eb07b4437d87adeaf6d47e05531ae97e8f2/scripts/gzdoom.sh), [Doom launch script](https://github.com/christianhaitian/dArkOS/blob/7b91fe0f37c82ed861482173d3cbec8ed1966f09/gzdoom/scripts/doom.sh)

No standalone port directory named Zandronum was found in the complete, nonrecursive PortMaster `ports` tree checked at commit `27922155273d25310e534a9388d557cbef1d94d5` (1,434 entries; not truncated). The earlier Christian Haitian PortMaster repository's complete tree also had no Zandronum-named path. This is a bounded negative finding, not proof that no personal or unofficial port exists anywhere. [Current PortMaster ports tree](https://github.com/PortsMaster/PortMaster-New/tree/27922155273d25310e534a9388d557cbef1d94d5/ports), [older PortMaster repository](https://github.com/christianhaitian/PortMaster/tree/4ee5bcc5bffa9d01d000da20f42a9de00207ddc3)

It offers useful launcher, controls and WAD-selection examples; it is not a Zandronum 3.2.1 port. ## Renderer and SDL choices

Inspection here uses upstream 3.2.1 release commit `28f736fb3f77bf0b767ec5468191bc05d0fccbb9`, identified in the separate upstream-version audit. Its Linux client uses SDL 1.2 APIs and has distinct software and OpenGL framebuffer implementations. The build has a `NO_GL` option; with OpenGL enabled it looks for OpenGL and GLU. Sound normally requires FMOD Ex. That is a substantial dependency gap against dArkOS's SDL2/GLES stack. [3.2.1 client build configuration](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/CMakeLists.txt), [software framebuffer](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/sdl/sdlvideo.cpp), [OpenGL framebuffer](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/sdl/sdlglvideo.cpp)

| Candidate | Evidence | What must be demonstrated |
| --- | --- | --- |
| Software world renderer, SDL presentation | Upstream has a software framebuffer and `NO_GL`. | Present frames through SDL2 KMSDRM, provide sound, measure CPU cost at native 640×480. CPU rendering still requires a working display backend. |
| Existing desktop OpenGL renderer through gl4es | Zandronum uses legacy desktop GL; gl4es translates desktop GL 1.5/2.1 onto GLES 1.1/2.0. | Working EGL/context creation and GL function loading on dArkOS, GLU handling, shader/extension correctness, visual parity, resource use. |
| Native GLES renderer | dArkOS already uses this route for modern GZDoom. | A renderer adaptation or backport plus validation that Zandronum game/network behavior stays 3.2.1-compatible. No native GLES backend was identified in the inspected Zandronum release. |
| Desktop GL via Panfrost or another display runtime | Exists in other distribution/runtime ecosystems. | Availability on the actual dArkOS image and any added runtime cost. It is not the initial assumption and does not justify changing firmware. |

The upstream GL interface checks for desktop GL 1.3, warns below 1.4 and uses higher GL/shader features when available; scene code includes immediate-mode `glBegin` calls. A GLES version number alone does not satisfy these desktop APIs. [GL feature detection](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/gl/system/gl_interface.cpp), [wall rendering](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/gl/scene/gl_walls_draw.cpp)

gl4es supports substantial legacy OpenGL functionality but documents limitations, including depth/stencil readback, selection and multiple color attachments. PortMaster documents its use for GLES-only handhelds. Its default GL setup selects desktop GL 2.1 over GLES2 and GBM/framebuffer output, with a fallback when `/dev/dri/card0` is absent. Treat that as a starting pattern, not a tested Zandronum configuration. [gl4es project](https://ptitseb.github.io/gl4es/), [PortMaster porting guide](https://portmaster.games/porting.html#gl4es), [PortMaster GL setup](https://github.com/PortsMaster/PortMaster-GUI/blob/61f346d72456a57a4069bdaaf1914c5f42b36fc2/PortMaster/libgl_default.txt)

For SDL there are two candidate experiments: implement or reuse a separately verified SDL2 migration, or retain SDL 1.2 calls using **sdl12-compat**, SDL's official source/binary compatibility layer over SDL2. This repository's legacy fork also uses SDL 1.2; it does not supply an existing SDL2 migration. The compatibility layer requires SDL2 at runtime and has documented caveats for OpenGL scaling and direct window-system access. It supplies the old SDL interface; it does not itself translate the application's desktop OpenGL calls to GLES. [Legacy fork audit](current-arm-fork.md), [sdl12-compat README](https://github.com/libsdl-org/sdl12-compat/blob/476f41c6159a58e72a1000501c56ed5bea288a0f/README.md)

**Accelerated-route recommendation — inference:** first test a minimal legacy-GL scene and Zandronum startup at native resolution using gl4es plus either sdl12-compat over dArkOS SDL2 or a reviewed SDL2 display migration. Validate EGL context creation, function loading and GLU before investigating renderer changes. Then measure base-game gameplay. A working mobile GPU and GLES driver make this route plausible; they do not establish direct desktop-GL compatibility, sufficient speed or visual correctness. A native GLES renderer would be a larger subsequent project if the wrapper fails. The user's interest in acceleration is distinct from a requirement for particular OpenGL effects; any visual-feature preference remains to be established after the experiments.

## Build and deployment implications

**Proposed approach — inference:** use an AArch64 Linux builder/sysroot that matches the installed dArkOS userland. An ARM64 Linux VM on the current macOS development machine is one possible builder. A native macOS ARM64 build has the wrong OS executable format and runtime dependencies. Record compiler, libc, C++ runtime, SDL, graphics and audio library versions; matching the CPU family alone is insufficient.

Upstream's cross-build support imports executables from a native build (`IMPORT_EXECUTABLES`), and asset packaging invokes `zipdir`. A cross-build therefore must account for build-host tools separately from target binaries, or use an ARM64 Linux build environment that can execute those tools. [3.2.1 top-level build](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/CMakeLists.txt)

A personal first deliverable can be a copied executable, matching engine PK3 files, selected libraries, a game config and an EmulationStation shell launcher. dArkOS accepts shell scripts in its Doom folder. A PortMaster-style launcher is optional but useful for device controls, logging, library lookup and cleanup. Formal public PortMaster submission is outside the user's initial personal-build requirement. [dArkOS Doom extensions](https://github.com/christianhaitian/dArkOS/wiki/dArkOS-Emulators-and-Ports-information#doom), [PortMaster launcher packaging examples](https://portmaster.games/packaging.html#opensource-game-example-launchscript)

If PortMaster integration is used, source the firmware-specific module and standard helpers rather than hardcoding paths from desktop Linux. The current dArkOS module includes PulseAudio directory and Mali library handling; this further argues for testing the actual installed PortMaster version. Public packaging would additionally need appropriate source/library/asset license notices. [dArkOS PortMaster module](https://github.com/PortsMaster/PortMaster-GUI/blob/61f346d72456a57a4069bdaaf1914c5f42b36fc2/PortMaster/mod_dArkOS.txt), [license packaging requirements](https://portmaster.games/packaging.html#licensefile)

## Controls, networking and acceptance evidence

Upstream supports joystick axes, hats and buttons; its default axis order does not establish that this R36S's mappings and deadzones are correct. Verify both sticks, shoulder buttons, menu movement, weapon selection, firing, use, automap and clean exit. PortMaster's Doom Engines shows a controller-only launcher and text-entry approach that may be reused as a design reference. [3.2.1 joystick support](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/sdl/i_joystick.cpp), [Doom Engines controls](https://github.com/PortsMaster/PortMaster-New/blob/27922155273d25310e534a9388d557cbef1d94d5/ports/doomengines/README.md)

dArkOS documents Wi-Fi configuration and requires a compatible USB dongle on devices lacking built-in Wi-Fi. SSH services must be enabled through Options for remote testing. A networked client also needs an ergonomic way to choose a server and load its exact content without relying on keyboard typing on the handheld. The Zandronum client already accepts `-connect`, so a predefined server launcher is a practical first experiment. [dArkOS Wi-Fi / SSH FAQ](https://github.com/christianhaitian/dArkOS/wiki/Frequently-Asked-Questions), [3.2.1 client connection arguments](https://github.com/TorrSamaho/zandronum/blob/28f736fb3f77bf0b767ec5468191bc05d0fccbb9/src/cl_main.cpp)

Acceptance should record an actual device session: launch from EmulationStation, visible gameplay, effects and music, controller-only basic play, config persistence, repeated launch/exit, and connection to an unmodified official 3.2.1 server using identical IWAD/add-on content. Measure frame time/FPS and memory at native 640×480 on representative base-game maps against the user's 30 FPS minimum / 60 FPS goal before selecting defaults. Reduced internal resolution is not an accepted substitute for this requirement. Add representative mods only after the base-game gate. No achieved FPS, broad mod compatibility, battery result or multiplayer reliability is claimed by this research.

## Questions requiring the user's device or preferences

1. Exact installed dArkOS image/update date and whether it is Christian Haitian's image with an R36S adaptation or a downstream build. Device inspection can establish OS version, kernel, board model, loaded graphics libraries and SDL version; a label alone cannot.
2. Actual network setup: built-in Wi-Fi, USB Wi-Fi adapter, other connection, or currently offline. The standard platform specification is insufficient to infer this unit's networking.
3. Which visual features matter if accelerated GL and software rendering both meet the performance target, or if only one route does. Investigate acceleration first; no renderer preference beyond that has been fixed.
4. A short reference-map list and how to assess the 30 FPS minimum during heavy scenes. For later mods, ask for exact titles/versions rather than promising all Zandronum mods on a 1 GB handheld.
5. First multiplayer workflow: a saved server/address with preloaded content, or an interactive controller-only server browser. The latter is additional UI scope.
6. Whether device access for deployment and measurements will be available during implementation. Source review and a build on another ARM machine cannot replace R36S runtime evidence.
