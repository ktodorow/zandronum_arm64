# Zandronum 3.2.1 Linux ARM64 client and R36S PortMaster adaptation

## Problem Statement

The owner wants a playable Zandronum 3.2.1 client on Linux ARM64 and on an R36S handheld running dArkOS. The immediate goal is to establish and test single-player Doom/Doom II gameplay. Multiplayer follows after that milestone, with the eventual requirement to play alongside existing PC clients on unmodified official 3.2.1 servers. A dedicated server or an executable that merely compiles does not meet the single-player goal.

The current repository contains a Pandora-derived Legacy ARM fork identifying itself as Zandronum 3.1-alpha. Its earlier ARM work does not establish a working AArch64 client. The requested upstream Git mirror's current master identifies itself as 3.3-alpha, so neither current branch head is the Release baseline. Starting from either without establishing the exact release identity would undermine the intended gameplay and multiplayer compatibility.

The R36S adds display, graphics-driver, controller, audio, memory, packaging, and performance constraints. These must first be resolved for local single-player play. In the later multiplayer milestone, the owner also wants to discover servers and obtain their required add-ons using the handheld alone. The existing engine browser can discover servers and join with local files, but it does not download missing content or establish exact file matches in its browser preflight.

## Solution

Create a reproducible, playable Linux ARM64 client from the exact official Zandronum 3.2.1 release. Selectively reuse reviewed fixes from the Legacy ARM fork, preserve existing repository history, and develop common ARM client changes on master. Maintain a dedicated R36S branch derived from that ARM master for device-specific adaptation.

Build in a disposable, pinned Linux ARM64 Docker environment on the owner's Mac, retain source and exported artifacts outside the disposable environment, and validate runtime behavior on the actual handheld. Deliver a personal PortMaster package targeting the inspected dArkOS installation.

**Milestone 1 — single-player:** Deliver and validate a personal R36S package with native 640×480 Doom/Doom II gameplay, responsive controller gameplay and menus, sound effects and base-game music, persistent settings and saves, normal map transitions, and clean launch and return through PortMaster. Investigate accelerated rendering first; either accelerated or software rendering is acceptable if it meets these gates. Require sustained at least 30 FPS in representative original-game maps and a heavier single-player combat scene, aim for 60 FPS, and record brief dips. This milestone can be accepted without server joins, browser improvements, multiplayer text entry, or add-on downloading.

**Milestone 2 — multiplayer, after single-player acceptance:** Prove Stock-server compatibility and complete the handheld multiplayer workflow with public and existing LAN discovery, useful filters and details, manual connection, controller text entry, and Handheld content setup. When required add-ons are absent or mismatched, retrieve available exact files, validate their identity and load order, and join on-device. Show progress, allow cancellation, and explain failures when the exact content cannot be obtained. Add stock-server multiplayer performance tests with the same native-resolution and sustained-FPS targets, and rerun single-player regression checks on the final package.

The owner supplies Doom/Doom II IWADs separately. Preserve the official release source and compatibility identity from the beginning so that later multiplayer work has the correct baseline; runtime multiplayer validation belongs to Milestone 2.

## Implementation Decisions

- **Release baseline:** Follow the accepted ADR choosing exact official Zandronum 3.2.1 rather than upgrading the Legacy ARM fork. Pin Mercurial tag `ZA_3.2.1`, changeset `a701547f4162dd965c25f082a55be2787310e6ea`, or its Git mirror equivalent `28f736fb3f77bf0b767ec5468191bc05d0fccbb9`. Current upstream master is not the selected release.
- **History and branches:** Preserve the existing legacy tip and commits when integrating the release. Develop common ARM client portability on master; derive and maintain a dedicated R36S branch for handheld changes. Keep fixes useful to both in the common base. Select exact Git integration operations during implementation without discarding history.
- **Client scope:** Build the graphical Linux ARM64 client with matching engine resources. Audit architecture detection, non-x86 code paths, assembly fallbacks, arithmetic, alignment, pointer-size assumptions, and remaining ARM-specific guards. Review legacy fixes individually; old 32-bit ARM compiler flags do not establish ARM64 support.
- **Milestone boundary:** Complete and accept the single-player build, PortMaster integration, local gameplay, audio, persistence, rendering, and representative performance before beginning multiplayer feature work and runtime tests. Browser improvements, server joins, multiplayer text entry, and content retrieval are later-milestone requirements. Existing upstream networking can remain in the client; its validation does not gate the first milestone.
- **Compatibility identity:** Preserve the official release's network compatibility identity independently of later port commits and expose the port's own provenance separately. The upstream revision generator uses a Mercurial commit timestamp in network version calculation. A Git-only or archive build must not fall back to zero, unknown metadata, or the timestamp of a port commit. Preserve release gameplay and content semantics now; runtime Stock-server compatibility is mandatory in Milestone 2 and cannot be claimed from Milestone 1 results.
- **Build environment:** Use a pinned, disposable Docker Linux ARM64 builder on the Mac. Debian 13 Trixie is the initial userland choice based on the inspected device. Pin the selected image and dependency/toolchain inputs, target an explicit ARMv8/RK3326-compatible CPU baseline, and avoid host-native CPU flags. Build-time resource generators must execute in the builder and export resources matching the client.
- **Artifact and cleanup contract:** Keep host source and exported binaries/resources separate from disposable project containers and build data. Provide repeatable build, export, deployment, and project-specific cleanup instructions or commands. Cleanup must preserve source and desired artifacts and be scoped to this project's environment.
- **Runtime dependencies:** Validate actual linked libraries and symbols against the device, including its custom SDL runtime and Mali-backed graphics libraries. Package-private dependencies and installed runtimes are implementation choices to verify. Package-manager version matching alone is insufficient.
- **Display and input platform:** Official 3.2.1 uses SDL 1.2 APIs. Evaluate sdl12-compat over the installed SDL2 runtime before deciding whether a reviewed SDL2 platform migration is necessary. Neither the release nor the Legacy ARM fork provides an already completed SDL2 migration. Preserve display, input, and audio behavior while changing the platform integration.
- **Audio:** Establish effects and base-game music without assuming the release's normal FMOD Ex runtime supports this ARM64 target. Review useful legacy OpenAL and decoder work and select a functioning target-compatible audio path.
- **Renderer:** Investigate native-resolution acceleration through the actual EGL/GLES and display stack, including gl4es as a candidate for the engine's desktop OpenGL requirements. GLES libraries alone do not establish desktop OpenGL or GLU compatibility. Keep a working software-renderer option. Choose either path that passes the same acceptance gates; if neither meets native 640×480 performance, revisit the plan rather than silently reducing internal resolution.
- **PortMaster integration:** Implement a personal package against the installed PortMaster/dArkOS launch contract, including path discovery, library/display setup, controller setup, logging, configuration/save persistence, helper lifecycle where applicable, and clean return. Owner requires **SELECT + START** as game exit combination. Always stop EmulationStation before each Zandronum device run/test to release RAM, then restore and verify the frontend after exit or failure. Detach the runner from the ES service control group before stopping it; follow the [required lifecycle](../portmaster-testing.md#required-emulationstation-lifecycle). Validate the physical controls instead of inferring mappings solely from firmware device aliases. Use native controller handling and mapping helpers where appropriate without duplicate input.
- **Browser reuse:** In Milestone 2, prefer extending the engine's existing graphical browser, master-server query, filters/details, local-content restart, and LAN broadcast reception. LAN acceptance uses the existing broadcast mechanism with suitably configured servers; an active LAN scanner is not required. Confirm readability and controller operation on the device.
- **Text entry:** In Milestone 1, support any entry essential to basic single-player menu/save operation using the controls. General controller text entry for manual addresses, applicable passwords, and filter or player configuration belongs to Milestone 2. An engine keyboard or a verified firmware helper is an implementation choice; the acceptance contract is completion without an external keyboard or desktop.
- **Content metadata and preflight:** Extend the browser/join boundary to retain and use authoritative required-file identities and order, including relevant optional-content and patch metadata. Distinguish absent files from same-name mismatches. Preserve the game's existing connection-time content checks. Do not infer exact identity solely from a filename or accept a download without the required validation.
- **Download integration:** Investigate a small Wadseeker-based helper or integration before adapting a full desktop browser. Wadseeker reuse is a candidate, not a committed dependency; validate build/runtime requirements and interface behavior. The content boundary must carry the selected server, required identities/order, progress, cancellation, and success/failure results through to restart and join. The engine remains the initial user-facing browser candidate.
- **Content failure behavior:** Use exact available required content, report unavailable files, reject wrong hashes and incomplete downloads, and surface network or storage failures. Do not silently replace required versions with similarly named files. Cancellation must return control to the handheld workflow without treating partial content as ready. Base-game IWADs remain owner-supplied rather than part of automatic add-on retrieval.
- **Implementation sequence:** Establish source identity and the builder; make the common ARM client playable locally; adapt the R36S PortMaster package, controls, audio, persistence, and renderer; measure representative single-player performance and accept the first personal package. Only then prove Stock-server compatibility, complete browser/text/content workflows, and measure multiplayer performance. Final overall acceptance includes both milestones and single-player regression checks. Single-player acceptance is a valid delivery gate on its own.

## Testing Decisions

- **Device workflow:** Follow the [PortMaster test workflow](../portmaster-testing.md) for personal-package layout, installed-helper checks, SSH deployment/log retrieval, physical-device launch/exit and staged single-player acceptance.
- **Confirmed primary boundary:** The owner confirmed testing through the packaged client launched from PortMaster on the actual R36S. Keep that primary acceptance seam, now applied first to single-player graphics, input, audio, persistence, and performance, and later to browser/content setup and multiplayer. Test observable player behavior and resulting artifacts rather than private functions, compiler guards, or a particular helper implementation.
- **Supporting checks:** Verify reproducible ARM64 client builds, target-compatible binary dependencies, matching generated resources, preserved release compatibility identity, and artifact export from a clean builder. Record image/toolchain inputs and source provenance. These prerequisites do not substitute for launching and playing the client. Verify project cleanup without removing source or exported artifacts.
- **Modules covered:** In Milestone 1, exercise the ARM client platform and renderer/audio integration, the R36S PortMaster lifecycle and controls, and persistence. In Milestone 2, add runtime release/network compatibility, the browser and general text entry, and content preflight/download/restart integration through the same boundary.
- **Single-player acceptance:** With owner-supplied Doom/Doom II data, test visible native-resolution rendering, movement/aiming/actions, menus and any essential single-player entry, effects/music, saves and settings across relaunch, normal map changes, and clean exit to the frontend. Confirm helpers do not leave interfering input or display state after exit. Accept this milestone from those results and its single-player performance evidence; network/server/download evidence is not required yet.
- **Later Stock-server compatibility:** After single-player acceptance, use an unmodified official Zandronum 3.2.1 server and an existing PC client with matching data. Require successful connection and active gameplay together, including map transitions and continued synchronization. A displayed 3.2.1 string, compile success, or source-derived protocol calculation is insufficient evidence.
- **Later discovery and controller workflow:** Exercise public discovery on the real network, controlled LAN servers using the existing broadcast mechanism, filters/details/list navigation, and manual connection. Complete all interaction with the handheld controls, including text entry where required.
- **Later content success cases:** On controlled stock 3.2.1 servers with obtainable test add-ons, cover already matching local content, absent content, and a same-name wrong-version file. Verify exact-file validation, required order, relevant optional/patch semantics, restart with the selected content, and successful gameplay. Include an end-to-end PortMaster launch → discover/select → download absent content → match → join → exit test.
- **Later content failure cases:** Use controlled download endpoints and server content to exercise unavailable exact files, wrong hashes, interrupted or incomplete transfers, cancellation, and observable network/storage errors. Require a readable failure and continued controller navigation, with invalid content never accepted as ready. Use a controlled storage fixture for exhaustion cases.
- **Focused tests only when needed:** Prefer covering content behavior through the complete client with controlled servers/downloads. If a failure condition cannot be exercised reliably there, add focused behavioral tests at the highest public content-helper boundary that accepts a requirement and returns validated content or an observable failure. Avoid adding separate seams for individual parsing, hashing, or UI internals.
- **Single-player performance acceptance:** Measure on the physical R36S using native 640×480 internal rendering and presentation. Cover representative original Doom/Doom II maps and a heavier single-player combat scene with active effects/music. Record the actual maps/scenes, repeatable durations, content identities, renderer/settings, sustained frame rate, and the depth/duration of brief dips. Require sustained at least 30 FPS in each representative test and aim for 60. A high whole-run average cannot mask a scene consistently below 30 FPS; lower-resolution scaling is not an accepted substitute. No multiplayer session is required to accept Milestone 1.
- **Later multiplayer performance and regression:** Add a representative stock-server multiplayer session in Milestone 2 with the same native-resolution and sustained-FPS requirements. Recheck affected single-player behavior and performance after multiplayer integration, and retain separate evidence for both milestones.
- **Mod limits:** Establish the original-game baseline first. Validate selected mods separately and report their results independently; successful content download or base-game performance does not prove arbitrary mod playability.
- **Existing prior art:** Repository inspection found no established automated graphical-client acceptance suite. Bundled library examples and the standalone UPnP utility are not prior art for this deliverable. Reuse the engine's existing launch, menu, connection, and demo facilities where useful for repeatable scenarios, and compare behavior with an official PC client. Replay or timed-demo measurements can supplement, but cannot replace live controller/audio/multiplayer tests.

## Out of Scope

- Multiplayer validation, browser enhancements, manual-server/password entry, and Handheld content setup are deferred from Milestone 1 to Milestone 2. They remain required for overall completion.
- ARM platforms other than Linux ARM64 in the initial delivery, including a native Apple Silicon macOS client and 32-bit ARM support.
- A dedicated-server-only port or a modified server/network protocol as the solution to client compatibility.
- Upgrading the Legacy ARM fork forward, adopting upstream 3.3 development as the Release baseline, or discarding legacy repository history.
- Public releases, PortMaster catalog submission, upstream contribution, and compatibility with every R36S firmware variant or other handheld.
- Docker as the game runtime on the R36S; Docker supplies the build environment, while the exported client runs through PortMaster on the device.
- Replacing the handheld firmware or treating installed desktop OpenGL libraries as proof of a working accelerated renderer.
- A requirement for OpenGL-only effects when another renderer meets all agreed gameplay and performance gates.
- Reduced internal resolution as a substitute for the native 640×480 acceptance target.
- Favorites, history, active LAN scanning, full Doomseeker feature parity, or a required full desktop Doomseeker UI.
- Automatic acquisition of commercial Doom/Doom II IWADs; these are supplied by the owner.
- A guarantee that every map, every moment, or arbitrary downloaded mods sustain 30–60 FPS; the agreed acceptance uses representative base-game and multiplayer tests and records brief dips.
